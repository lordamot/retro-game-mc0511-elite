# RT-11 lifecycle and persistent data

## Runtime contract

The supplied base volume is RT-11 SJ V05.04 G. The disk is 819,200 bytes,
1600 blocks of 512 bytes, with the normal monitor bootstrap. `STARTS.COM`
sets both required options and starts the game:

```text
SET USR SWAP
SET EXIT SWAP
R ELITE
```

The monitor must supply user memory through octal `146400`. USR NOSWAP
leaves too little on this volume. EXIT NOSWAP is not supported: swap-file
writes can make subsequent boots fail even if the first launch works.
The volume must be writable for `SWAP.SYS`, including load-only sessions.
Other monitor configurations require independent validation.

`ELITE.SAV` and `ELITE.DAT` contain matching 32-byte build identity headers.
Startup checks the pair before PPU takeover. Keep matching files together
on `DK:`. This identity check does not replace the resource bounds checks
or validate arbitrary commander contents.

## File I/O

| File | Use | Channel |
|---|---|---:|
| `ELITE.DAT` | Overlay directory, key file, overlays, hull bank, mission text | 0 |
| `ELSAV1.DAT` … `ELSAV4.DAT` | Two-block commander slot files | 1 |

Resources use `.LOOKU` and `.READW`. Constants named `*_LBA` and manifest
entry offsets are **file-relative DAT blocks**, not physical floppy
addresses. Physical relocation of DAT must not affect the game.
`DATA_READ` checks block bounds, word count, buffer alignment and memory
range, and retries failed reads. A fatal resource failure restores the
terminal and reports an error instead of executing stale overlay code.

Save replacement uses `.ENTER`, `.WRITW` and `.CLOSE`; a failed tentative
write is `.PURGE`d. A full volume must preserve previous permanent files.
Slots are created when first saved. Docking and capsule rescue autosave;
the access menu supports explicit save/load. Failed autosave displays
«ОШИБКА: КОМАНДИР НЕ СОХРАНЕН».

Loads stage the complete file, validate its length, signature and version,
and only then replace the live pilot. Failed loads retain the current
commander and slot. Validation is not a checksum of every record byte.
Menu browsing caches slot names; successful saving invalidates that cache.

## CPU/PPU ownership

CPU vectors and monitor service remain RT-11's. The stack, request blocks
and PPU mailboxes stay resident below the swapped USR area. The overlay
window may be swapped during a file call; asynchronous state must not live
there. Save staging uses drained segment buffers, not the active overlay.

All native resource and commander calls keep `RT_IOBUSY` set while RT-11
works. The PPU defers longer input-publication, tune and effect work while
retaining firmware motor bookkeeping. Removing this guard causes firmware
read errors under repeated I/O. Keyboard IRQs retain pending edges and
publish them after I/O, even when a press and release both occur during it.
The published CPU clock is also deferred, so `OVL_TK` is unsuitable as an
accurate native disk-latency timer.

## Clean exit

АР2 then Ч, or PC Tab then X, exits without autosaving. The exit path:

1. Drains rendering and stops publication and audio.
2. Restores the PPU firmware line-table memory, display state, keyboard,
   timer and channel vectors, and receiver enables.
3. Releases the PPU cache and program allocations.
4. Restores the CPU console, purges open channels, restores the original
   stack and returns through `.EXIT`.

A later `R ELITE` must work in the same monitor session. The PPU allocation
contains a 2392-byte firmware backup plus saved scalar state. K2 copy
request 20 does not report completion through the allocation error byte;
execute request 30 follows it, and the game waits for its ready flag.
Only allocation/free requests use the error-status wait.

## Updating a player disk

```sh
make build
python3 tools/play_disk.py build/elite.dsk saves/elite.dsk --manifest build/manifest.json
```

`make run` performs this refresh before launching SDL. Use `PLAY_DSK` for a
different player image. Keep persistent disks outside `build/`, which
`make clean` removes.

Refresh preserves all four named commander files, including records the
game would reject. It constructs the new volume from the build base,
writes a temporary `.new` image, retains the preceding image as `.bak`,
and publishes atomically. It replaces other files; preserve unrelated
user-added files separately. Backups are one preceding version, not a
multi-version archive.

Recognized legacy raw images migrate the four two-sector slots at physical
blocks 100–107 without changing their bytes. The recognizer checks the
bootstrap instruction prefix; a NOP alone is not sufficient to identify a
legacy disk. Unknown image formats, unexpected sizes or invalid legacy
records must fail without replacing the destination. Record versions are
not translated. These physical block numbers belong only to migration,
never to native runtime I/O.

The build also retains recognized commanders from an existing build disk;
verification reconstructs pristine disks from the manifest and uses private
copies under `tmp/`. See [testing](testing.md) and the
[tool skill](../.agents/skills/elite-tools/SKILL.md).
